**Планирование: анализ, идентификация проблем и поиск решений**

### 1. Анализ архитектуры и идентификация проблем

На основе предоставленной диаграммы C4 (уровень контейнеров) и описания компании можно выделить следующие существующие и потенциальные проблемные места. Проблемы сгруппированы по областям.

#### 1.1. Надёжность и потеря заказов
- **Ненадёжная асинхронная интеграция.** CRM и MES обмениваются сообщениями через RabbitMQ, однако не описаны механизмы повторной обработки, Dead Letter Queue (DLQ) или идемпотентности. Это приводит к тому, что сообщения о смене статусов могут теряться, и заказы «зависают» на неопределённое время.
- **Отсутствие мониторинга очередей.** Нет данных о длине очередей, возрасте сообщений, ошибках доставки – проблемы с заказами обнаруживаются только по жалобам клиентов.
- **Прямой доступ внешних API‑пользователей к MES API.** Открытие API для партнёров создало дополнительный канал поступления заказов без контроля потока. При перегрузке MES или сбоях партнёры не получают ответа, и заказы теряются ещё на этапе расчёта стоимости.
- **Неопределённость сценария расчёта стоимости.** Расчёт может занимать до 30 минут. Синхронное ожидание HTTP-ответа от MES API на такое время рискованно; неизвестно, предусмотрен ли асинхронный callback. Это может приводить к тайм-аутам и «потерянным» запросам.

#### 1.2. Производительность и масштабируемость
- **Единственный инстанс каждого сервиса и базы данных.** Все компоненты (MES API, CRM API, Shop API, базы данных) работают в одном экземпляре. При линейном росте нагрузки (+100 заказов/месяц) и добавлении внешнего API система упирается в потолок производительности.
- **Длительная загрузка дашборда MES.** Операторы жалуются, что первая страница со списком заказов прогружается медленно, несмотря на фильтр по статусам и пагинацию. Это указывает на неоптимальные запросы к MES DB, отсутствие индексов или блокировки при одновременном расчёте стоимости.
- **Конкуренция вычислительных ресурсов.** Расчёт стоимости (2–30 минут CPU‑интенсивной работы) выполняется в том же процессе MES API, что и остальные операции (дашборды, обновление статусов). В результате ухудшается время отклика для всех пользователей.
- **Общая база данных Shop DB для CRM и Интернет-магазина.** Обе системы читают и пишут в одну БД, что создаёт contention по блокировкам и усугубляет деградацию при росте транзакций.
- **Отсутствие репликации БД.** Единственный инстанс работает и на чтение, и на запись, не позволяя разнести нагрузку.

#### 1.3. Инфраструктура и отказоустойчивость
- **Отсутствие балансировщиков и многозонального развёртывания.** Выход из строя одного EC2‑инстанса приводит к полной недоступности сервиса.
- **Одиночный узел RabbitMQ.** Без кластеризации брокер является единой точкой отказа и не масштабируется.
- **Нет API Gateway.** Прямой доступ к MES API из интернета для внешних партнёров не позволяет ограничивать частоту запросов, применять политики безопасности и изолировать трафик.

#### 1.4. Процессы CI/CD и качество
- **Задержки релизов из‑за ручного тестирования.** E2E‑сценарии выполняет вручную один QA‑инженер. Любой баг уровня high/highest блокирует релиз на недели, что замедляет доставку критических исправлений.
- **Отсутствие автоматизации E2E и интеграционных тестов.** QA уже создавал прототипы, но полноценного набора автотестов нет. Это увеличивает цикл обратной связи.
- **Ручной деплой в release и prod.** Замедляет развёртывание, повышает риск ошибок при выкатке.

#### 1.5. Архитектурные дисбалансы
- **Разные технологические стеки (Java + C#) без стандартизации взаимодействия.** Интеграция «заказ в CRM через очередь от MES» частично написана командой, возможна несогласованность форматов и обработки ошибок.
- **Распределённая статусная машина без единого источника истины.** Статусы меняются в трёх системах, консистентность зависит от корректной доставки сообщений. Отсутствует механизм восстановления рассогласований.
- **Онлайн-магазин не участвует в расчёте цены, но отвечает за создание заказа.** При долгом расчёте клиент может не дождаться подтверждения, уйти или создать дубликат.

### 2. Инициативы по устранению проблем

Каждая инициатива направлена на одну или несколько выявленных проблем. Список сформулирован в виде конкретных шагов, которые можно планировать в спринтах.

1. **Внедрить мониторинг и гарантированную доставку сообщений RabbitMQ**
   - Настроить Dead Letter Queue и политики повторных попыток для всех критических событий заказов.
   - Добавить метрики (длина очереди, возраст сообщений, количество DLQ‑сообщений) и алерты в систему мониторинга (Prometheus/Grafana).
   - Реализовать идемпотентные обработчики сообщений в CRM API и MES API, чтобы исключить дублирование смен статусов.

2. **Оптимизировать дашборд MES и снизить нагрузку на MES API**
   - Провести аудит запросов к MES DB: добавить недостающие индексы, переписать «тяжёлые» запросы.
   - Внедрить кэширование списка заказов для операторов (Redis) с инвалидацией при изменении статусов.
   - Перевести генерацию дашборда на read‑реплику MES DB, когда она появится.

3. **Выделить расчёт стоимости в отдельные фоновые воркеры**
   - Отделить синхронную обработку API‑запросов (получение задания на расчёт) от длительного вычисления. MES API должен принимать запрос, регистрировать задание в БД и ставить задачу в очередь (на базе RabbitMQ или отдельного механизма).
   - Запустить несколько инстансов «worker‑ов» для параллельной обработки расчётов, что ускорит общее время ответа и изолирует CPU‑нагрузку.

4. **Масштабировать сервисы и базы данных**
   - Развернуть MES API и CRM API в нескольких экземплярах за балансировщиком (ALB/ELB).
   - Настроить репликацию для MES DB и Shop DB: одна мастер‑нода на запись, одна или несколько read‑реплик для отчётов и дашбордов.
   - Перевести RabbitMQ в кластер либо мигрировать на управляемый сервис очередей (Amazon MQ / Yandex Managed Service for RabbitMQ) с поддержкой высокой доступности.

5. **Ввести API Gateway для внешних партнёров**
   - Разместить перед MES API шлюз (Kong, Yandex API Gateway, Spring Cloud Gateway), который будет выполнять аутентификацию, rate limiting и маршрутизацию.
   - Изолировать трафик API‑пользователей от внутреннего трафика операторов, при необходимости выделить отдельные пулы инстансов.

6. **Автоматизировать E2E‑тестирование и улучшить CI/CD**
   - Совместно с QA‑инженером разработать и внедрить фреймворк для автоматического прогона критических E2E‑сценариев (Playwright/Cypress).
   - Запускать автотесты на стадии pull request и в рамках развёртывания на staging‑окружении.
   - Добавить staging‑окружение, идентичное production, с автоматическим деплоем после успешного прохождения тестов.
   - Перевести деплой в release и prod на автоматический (с ручным подтверждением), чтобы исключить ошибки ручного ввода.

7. **Обеспечить трассировку заказов и аудит статусов**
   - Внедрить распределённую трассировку (Jaeger/Zipkin) с передачей trace‑id между сервисами через HTTP‑заголовки и сообщения RabbitMQ.
   - Создать админ‑панель для службы поддержки с поиском заказа по сквозному идентификатору и отображением истории статусов.

8. **Изолировать Shop DB для разных контекстов**
   - Постепенно выделить CRM в отдельную базу данных или хотя бы в отдельную схему, чтобы снизить конкуренцию блокировок между операциями интернет-магазина и CRM.
   - Синхронизацию необходимых данных реализовать через события в RabbitMQ или CDC.

9. **Улучшить UX для операторов и внедрить приоритизацию**
   - В дашборде MES по умолчанию показывать только новые заказы (со статуса PRICE_CALCULATED и выше), ограничив количество строк с серверной пагинацией.
   - Рассмотреть механизм бронирования заказа оператором без обновления всей страницы (WebSocket или SSE) для устранения «гонок».

10. **Повысить устойчивость HTTP‑взаимодействий**
    - Для внешних API‑запросов расчёта цены использовать асинхронный паттерн: немедленно возвращать идентификатор задания, а результат отправлять через webhook или предоставлять по polling.
    - Для внутренних сервисов внедрить retry и circuit breaker (Resilience4j) при вызовах MES API из CRM API.

11. **Усилить команду с учётом планов**
    - Нанять разработчика C#/.NET (второго) для поддержки MES, особенно с учётом грядущей доработки воркеров и рефакторинга.
    - Добавить инженера по автоматизации QA, чтобы ускорить внедрение автотестов.
    - Рассмотреть привлечение DevOps‑специалиста с опытом облачной инфраструктуры для масштабирования.

### 3. Приоритизация инициатив и целевая архитектура

#### 3.1. Ход рассуждений
Ситуация критическая: бизнес теряет контракты и клиентов, поэтому первые шаги должны **стабилизировать текущую систему** и остановить потерю заказов. Затем необходимо **повысить производительность** для операторов и партнёров, чтобы вернуть к SLA. Третий фокус – **ускорить цикл поставки исправлений**, так как длительные релизы блокируют оперативное решение инцидентов.

Исходя из этого, высший приоритет получают инициативы, напрямую влияющие на целостность заказов и видимость проблем (мониторинг очередей, DLQ). Второй приоритет – оптимизация дашборда и выделение ресурсоёмкого расчёта, потому что медленная работа MES напрямую тормозит операторов и внешних партнёров. Третий – автоматизация тестирования и CI/CD, чтобы сократить Time‑to‑Market для исправлений.

#### 3.2. Целевая архитектура через полгода
Через шесть месяцев система должна представлять собой:
- **Масштабируемое облачное решение** с несколькими инстансами MES API и CRM API, балансировщиками нагрузки и репликацией баз данных.
- **Вынесенный в отдельный слой расчёт стоимости** – задание попадает в очередь, обрабатывается пулом воркеров, результат сохраняется в БД и через событие уведомляет другие сервисы.
- **Надёжную шину сообщений** – кластеризованный RabbitMQ (или управляемый сервис) с мониторингом, алертингом, Dead Letter Queue и идемпотентными потребителями.
- **API Gateway** для внешних партнёров с ограничением скорости и асинхронным API расчёта, гарантирующим доставку результата.
- **Дашборд MES** с целевым временем отклика до 2 секунд благодаря индексам БД, кэшированию и чтению с реплик.
- **Полный CI/CD pipeline**: автотесты E2E при каждом PR, автоматический деплой на staging, ручное подтверждение для production; релизный цикл сокращён с недель до дней.
- **Сквозную трассировку** заказов, позволяющую в реальном времени находить «застрявшие» позиции.

#### 3.3. Три ключевые инициативы на ближайшие полгода
Если оставить только три инициативы, они должны дать максимальный эффект по правилу «остановить кровотечение – ускорить – закрепить».

1. **Построение надёжной асинхронной интеграции и мониторинга RabbitMQ** (инициатива 1 + частично 7).  
   *Почему:* это напрямую решает главную боль бизнеса – потерянные и просроченные заказы. DLQ, повторы и мониторинг позволят перестать терять сообщения и быстро обнаруживать проблемы. Без этого любые оптимизации бесполезны, потому что заказы всё равно будут исчезать.

2. **Оптимизация дашборда MES и вынос расчёта стоимости в воркеры** (инициативы 2 и 3).  
   *Почему:* медленный дашборд парализует работу операторов, а конкуренция за CPU между расчётом и штатными запросами усугубляет ситуацию. Выделение воркеров немедленно повысит отзывчивость MES для всех пользователей, включая внешние API. После этих мер можно будет обрабатывать возросший поток заказов без деградации.

3. **Автоматизация E2E‑тестирования и настройка staging‑окружения** (инициатива 6).  
   *Почему:* текущая практика ручного тестирования задерживает выпуск исправлений. Автотесты сократят цикл релиза с недель до дней, позволяя быстрее реагировать на инциденты и внедрять следующие улучшения. Это необходимый фундамент для безопасного масштабирования сервисов в будущем.

Эти три инициативы, выполненные в указанном порядке, создадут устойчивую основу для дальнейшего масштабирования и эволюции архитектуры, остановят отток клиентов и восстановят доверие партнёров.
