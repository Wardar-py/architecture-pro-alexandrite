# Архитектурное решение по трейсингу

## 1. Анализ системы и определение границ трейсинга

Для обеспечения сквозной видимости заказа необходимо покрыть трейсингом все компоненты, через которые проходит жизненный цикл заказа. Анализ текущей C4-диаграммы и бизнес-процесса показывает следующие критичные точки, где заказ может «зависнуть»:
- **Shop API** (Spring Boot) – принимает запросы от интернет-магазина, сохраняет заказ в Shop DB, инициирует процесс расчёта через вызов MES API (через очередь).
- **CRM API** (Spring Boot) и **CRM** (Vue) – обрабатывают подтверждение заказа, отправляют сообщения в очередь.
- **MES API** (C#) – рассчитывает стоимость, управляет назначением операторов, сохраняет статусы в MES DB.
- **RabbitMQ** – брокер сообщений, связывающий CRM и MES, а также возможные другие асинхронные взаимодействия.
- **Shop DB** и **MES DB** (PostgreSQL) – хранилища состояний.
- **3D files storage** (S3) – место хранения моделей, которое используется MES API при расчёте.

Особое внимание следует уделить асинхронным границам: потере сообщений в RabbitMQ, дублированию, отсутствию сквозного идентификатора при переходе из одного сервиса в другой. Также критичен долгий синхронный расчёт стоимости, который может обрываться по таймауту.

**Вывод:** трейсингом необходимо покрыть все API (Shop, CRM, MES), RabbitMQ (инструментирование публикации и потребления), взаимодействие с S3.

## 2. Данные, включаемые в трейсинг

Для эффективного поиска и анализа инцидентов в трейсы должны попадать:

- **Сквозной идентификатор заказа** (orderId) – проставляется на самом раннем этапе (Internet Shop) и передаётся во все последующие вызовы.
- **Идентификатор трассировки** (traceId) и **идентификаторы спанов** (spanId).
- **Название сервиса/компонента** (service.name), в котором исполняется код.
- **Тип операции** (span kind: `SERVER`, `CLIENT`, `CONSUMER`, `PRODUCER`).
- **HTTP-атрибуты** (метод, URL, статус-код, размер тела ответа).
- **Атрибуты сообщений RabbitMQ** (exchange, routing key, message id, время публикации/потребления).
- **Запросы к БД** (название таблицы, выполняемая операция, количество затронутых строк).
- **Ошибки и исключения** (сообщение об ошибке, стектрейс).
- **Время выполнения ключевых операций** (расчёт стоимости, запросы к БД, вызовы API).
- **Пользовательские свойства** (статус заказа, идентификатор пользователя/оператора).

## 3. Мотивация

Внедрение распределённого трейсинга необходимо по следующим причинам:

- **Сокращение времени на диагностику**. Сегодня команда тратит часы на ручное сопоставление логов из разных сервисов, чтобы понять, где заказ «застрял». Трейсинг визуализирует путь заказа и подсвечивает медленные/ошибочные спаны.
- **Восстановление доверия клиентов и партнёров**. Быстрое устранение потерь заказов и задержек напрямую влияет на удовлетворённость и удержание клиентов.
- **Выявление скрытых дефектов интеграции**. Трейсинг покажет рассогласование статусной машины, пропуски сообщений, повторные обработки.
- **Повышение производительности команды**. Разработчики и QA смогут самостоятельно исследовать инциденты, не привлекая смежников.
- **База для автоматизации SLA**. На основе данных трассировки можно строить метрики длительности обработки заказов и настраивать оповещения.

**Технические и бизнес-метрики, на которые повлияет трейсинг:**
1. **MTTR** – среднее время восстановления после сбоя заказа.
2. **Процент заказов, завершённых в рамках SLA** (например, 3 недели).
3. **Доля потерянных сообщений** (сообщения без завершения обработки).
4. **Время выполнения расчёта стоимости** (P95, P99), что влияет на обязательства перед партнёрами.
5. **Количество заказов, требующих ручного вмешательства** (администратором/поддержкой).


## 4. Предлагаемое решение

Для реализации трейсинга предлагается использовать стек на базе **OpenTelemetry**. Он обеспечит:
- **Единую интрументацию** всех сервисов: Java (Shop API, CRM API) – через OpenTelemetry Java agent (автоматическая интрументация Spring Boot, DB клиентов, RabbitMQ); C# (MES API) – через OpenTelemetry .NET SDK. Фронтенды (Vue, React) могут передавать сгенерированный на backend trace-id в пользовательский интерфейс для удобства отладки.
- **Передачу контекста** между сервисами: HTTP-заголовки и свойства сообщений RabbitMQ. Это гарантирует связность цепочки.
- **Сбор и экспорт телеметрии**: развернуть **OpenTelemetry Collector** в качестве промежуточного шлюза, который будет принимать трассировочные данные по протоколу OTLP, обогащать их, маскировать чувствительные поля и направлять в хранилище.
- **Хранение и визуализация**: использовать **Grafana Tempo** как backend для трейсов. UI предоставляет Grafana с дашбордом поиска и просмотра трейсов.

## 5. Компромиссы

- **Невозможность инструментировать внешние зависимости:** если партнёры используют собственные системы, взаимодействующие с API, они не передадут наш trace‑id. В таких точках цепочка может разрываться, и нам придётся полагаться на логи по orderId.
- **Накладные расходы:** внедрение трейсинга добавляет небольшую задержку на создание спанов. Для высоконагруженного MES API, особенно при расчёте стоимости, нужно тестировать производительность.
- **Незрелость инструментария C#:** OpenTelemetry .NET быстро развивается, но может отставать от Java‑агента в части автоматической интрументации RabbitMQ.
- **Обслуживание дополнительной инфраструктуры:** потребуется поддерживать Collector, Tempo, Grafana, что увеличивает нагрузку на DevOps.
- **Частичное покрытие на первых этапах:** полная инструментация всех сервисов займёт несколько спринтов. Команда может начать с MES API и CRM API, постепенно расширяя покрытие.

## 6. Аспекты безопасности

Для защиты данных трейсинга, которые могут содержать идентификаторы заказов и пользователей, необходимо:

- **Аутентификация и авторизация в Grafana:** доступ к дашбордам трейсов имеют только сотрудники инженерной команды и поддержки с ролью «Developer» или «Support». Интеграция с LDAP или OAuth2 провайдером компании.
- **Маскирование чувствительных данных в Collector:** настроить процессоры для удаления или замены персональных данных перед записью в Tempo. Например, маскировать полные имена клиентов, адреса.
- **Шифрование трафика:** OTLP между сервисами и Collector, а также между Collector и Tempo должен идти по TLS. Внутренние коммуникации внутри облака – по приватным каналам.
- **Изоляция хранилища:** Tempo разворачивается в отдельной подсети, доступ к его API разрешён только Collector и Grafana.
- **Аудит доступа:** вести лог запросов к трейсам с указанием пользователя и времени.

## 7. Автоматический мониторинг процесса заказа и алертинг

На основе данных трейсинга можно реализовать проактивный контроль прохождения заказов.

**Подход:**  
OpenTelemetry Collector может генерировать метрики из спанов (например, длительность выполнения операции «расчёт стоимости», время нахождения заказа в определённом статусе). Эти метрики поступают в Prometheus с лейблами `order_status`, `channel`. Далее Prometheus Rule описывает условия аномалий, а Alertmanager отправляет алерты.

**Сценарий мониторинга:**
- Отслеживается среднее время пребывания заказа в статусе `SUBMITTED` (от отправки до начала расчёта). Если за 10 минут заказ не перешёл в `PRICE_CALCULATED`, генерируется алерт.
- Контроль целостности сообщений через анализ спанов потребления: если для спана‑продюсера нет соответствующего спана‑консюмера в течение N минут – алерт о потерянном сообщении.
- Для API‑пользователей: если количество заказов, зависших в статусе `SUBMITTED` > 5, оповещать поддержку.
