# Архитектурное решение по кешированию

## 1. Мотивация

### 1.1. Проблемы
- **Медленная загрузка дашборда MES**: первая страница со списком заказов загружается долго, несмотря на пагинацию. Операторы жалуются, что это замедляет их работу.
- **Высокая нагрузка на MES API и MES DB**: частые запросы к базе данных при каждом открытии или обновлении дашборда, особенно в пиковые часы.
- **Рост заказов на 100 ежемесячно** и подключение внешних партнёров через API усугубляют проблему.

### 1.2. Что даст кеширование
- **Снижение времени отклика** дашборда до целевых 1–2 секунд.
- **Уменьшение нагрузки на базу данных** за счёт обслуживания повторяющихся запросов из кеша.
- **Повышение удовлетворённости операторов** и, как следствие, скорости обработки заказов.
- **Стабилизация работы MES API** при пиковых нагрузках.

### 1.3. Элементы системы, включаемые в кеширование
- **Список заказов для операторов** (GET /orders с параметрами `status`, `page`, `size`).
- **Детальная информация о заказе** (GET /orders/{id}) – используется реже, но также может кешироваться для быстрого просмотра.


## 2. Предлагаемое решение

### 2.1. Тип кеширования: серверное
**Клиентское кеширование** не подходит, потому что:
- Данные должны быть максимально актуальными, особенно при назначении заказов.
- Несколько операторов работают одновременно, и каждый должен видеть консистентную картину.

### 2.2. Паттерн кеширования: Cache-Aside

**Cache-Aside:**
  - При чтении: приложение проверяет кеш. Если данные есть – возвращает их. Если нет – загружает из БД, сохраняет в кеш и возвращает.
  - При записи: приложение обновляет БД и сразу инвалидирует соответствующий ключ кеша, чтобы при следующем чтении данные были загружены заново.

**Почему он подходит:**
  - Кеш заполняется только теми данными, которые действительно запрашиваются.
  - Отказоустойчив: если кеш недоступен, приложение работает напрямую с БД.
  - Прост в реализации и не замедляет операции записи.

**Сравнение с другими паттернами:**

| Критерий                   | Cache-Aside                                                 | Write-Through                        | Refresh-Ahead                                   |
|----------------------------|-------------------------------------------------------------|--------------------------------------|-------------------------------------------------|
| **Влияние на запись**      | Нет задержки                                                | Синхронная запись в кеш и БД         | Требует точной настройки времени обновления     |
| **Согласованность данных** | Возможна кратковременная несогласованность между кешем и БД | Строгая согласованность              | Согласованность зависит от интервала обновления |
| **Сложность реализации**   | Низкая                                                      | Средняя                              | Высокая                                         |
| **Устойчивость к сбоям**   | Высокая                                                     | При сбое кеша запись может не пройти | Зависит от актуальности данных в кеше           |

### 2.4. Стратегия инвалидации кеша

**Основная стратегия – инвалидация по ключу.**
При любом изменении заказа MES API явно удаляет из Redis все затронутые ключи списков заказов по соответствующим статусам и конкретный ключ `order:{id}`.
Это гарантирует, что следующий запрос получит свежие данные из БД.

**Дополнительная стратегия – временная инвалидация.**
Для всех кешированных данных устанавливается время жизни 60 секунд.
TTL также позволяет автоматически удалять редко запрашиваемые страницы, освобождая память.

**Почему не другие стратегии:**
- **Чисто временная**: обновление будет происходить с задержкой до 60 секунд, что приведёт к несогласованности у разных операторов и возможному дублированию взятия заказа.
- **Write-Through**: замедляет операцию записи, требует синхронной блокировки, что критично для интерфейса оператора.
- **Refresh-Ahead**: не подходит из-за непредсказуемых изменений; настройка интервала может привести либо к лишним запросам, либо к просроченным данным.

### 3. Заключение

Внедрение серверного кеширования с паттерном Cache-Aside и программной инвалидацией по ключу позволит:
- Снизить время загрузки дашборда MES до целевых значений.
- Уменьшить нагрузку на базу данных без ущерба для актуальности данных.
- Масштабировать систему при дальнейшем росте количества заказов.
