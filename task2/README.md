**Задание 2. Выбор и настройка мониторинга в системе**

### Мотивация

Внедрение полноценного мониторинга необходимо для:
- **Раннего обнаружения сбоев** – мы узнаем о проблемах до того, как они станут жалобами клиентов.
- **Понимания узких мест** – увидим, какой именно компонент деградирует под нагрузкой.
- **Обоснованных решений по масштабированию** – поймём, когда действительно нужно добавлять ресурсы.
- **Повышения доверия партнёров** – обеспечим SLA и прозрачность работы API.
- **Снижения времени на диагностику** – инженеры смогут быстро локализовать инциденты.

Бизнес получит измеримые показатели качества услуги, сократит потери контрактов и повысит удовлетворённость клиентов.

### Выбор подхода к мониторингу

- **Для HTTP API** (Shop API, CRM API, MES API) используем метод **RED**. Это напрямую отражает пользовательский опыт как для внутренних, так и для внешних клиентов.
- **Для инфраструктурных компонентов** (базы данных, RabbitMQ, инстансы) применяем метод **USE**. Это позволит выявить нехватку ресурсов и перегрузку на ранней стадии.

### Метрики и их обоснование

| Компонент / уровень       | Метрика                                                  | Зачем нужна                                                                           |
|---------------------------|----------------------------------------------------------|---------------------------------------------------------------------------------------|
| **Shop API**              | Number of requests (RPS)                                 | Базовый показатель нагрузки от интернет-магазина                                      |
|                           | Response time (latency)                                  | Время ответа пользователям; рост p99 может указывать на деградацию                    |
|                           | Number of HTTP 200 / 4xx / 500                           | Уровень ошибок (RED). Рост 500 сигнализирует о проблемах в API или зависимых сервисах | 
|                           | CPU % / Memory utilisation                               | USE – утилизация ресурсов инстанса                                                    |
|                           | Kb transferred (sent/received)                           | Характер трафика, аномалии                                                            |
| **CRM API**               | Number of requests (RPS)                                 | Нагрузка от внутренних пользователей (продавцов)                                      |
|                           | Response time (latency)                                  | Отзывчивость интерфейса CRM                                                           |
|                           | Number of HTTP 200 / 500                                 | Ошибки обработки заказов, интеграции с MES                                            |
|                           | CPU % / Memory utilisation                               | Выявление перегрузки инстанса                                                         |
| **MES API**               | Number of requests (RPS)                                 | Разделение трафика: от операторов (web) и от внешних API-партнёров                    |
|                           | Response time (latency)                                  | Критично для операторов и партнёров; долгий ответ ведёт к жалобам                     |
|                           | Number of HTTP 200 / 500                                 | Ошибки расчёта стоимости, получения списка заказов                                    |
|                           | CPU % / Memory utilisation                               | Основной потребитель ресурсов из-за расчёта 3D; требует пристального внимания         |
|                           | Доля запросов, закончившихся таймаутом                   | Партнёры теряют заказы при синхронном ожидании >30 мин                                |
|                           | Время выполнения расчёта стоимости (гистограмма)         | Выявляет аномалии сложных моделей, влияет на SLA                                      |
| **RabbitMQ**              | Number of messages in flight (ready / unacknowledged)    | USE – насыщение очереди, может указывать на медленных потребителей                    |
|                           | Number of dead-letter-exchange letters                   | Ошибки обработки: потерянные сообщения о статусах заказов                             |
|                           | Message age (самая старая готовая message)               | Задержка обработки сообщений, риски просрочки заказов                                 |
|                           | Number of published / delivered / acknowledged           | Профиль потока, расхождения в скорости публикации и потребления                       |
| **Базы данных**           | Number of connections (Shop DB, MES DB)                  | Saturation – приближение к лимиту соединений вызывает отказы                          |
|                           | CPU % / Memory utilisation / Disk IO                     | USE – ресурсы инстанса БД                                                             |
|                           | Размер базы данных (storage)                             | Планирование capacity, предотвращение переполнения                                    |
|                           | Number of deadlocks / slow queries (дополнительно)       | Качество работы с БД, причины медленного дашборда MES                                 |
| **3D files storage (S3)** | Size of S3 storage                                       | Отслеживание роста объёма файлов                                                      |
|                           | Number of requests (PUT/GET) и ошибки доступа            | Доступность файлов для расчёта                                                        |
| **Бизнес-уровень**        | Количество заказов по статусам (дополнительно)           | Воронка заказов; застревание в статусах – признак проблем интеграции                  |
|                           | Время нахождения заказа в каждом статусе (дополнительно) | SLA для партнёров, выявление узких мест процесса                                      |


### План действий

- Развернуть time-series базу данных VictoriaMetrics (или Prometheus) в облаке (Yandex Managed Service for Prometheus).
- Настроить сбор метрик с инфраструктурных узлов (EC2).
- Подключить экспортёры для RabbitMQ, PostgreSQL, S3.
- Интегрировать сбор метрик приложений: для Spring Boot (Shop API, CRM API) – Micrometer + Prometheus; для MES API (C#) – App Metrics или Prometheus.AspNetCore. Все приложения должны отдавать метрики на endpoint /metrics.
- Создать дашборды в Grafana:
     - **Обзорный (Overview):** RPS, latency, ошибки по всем API, статусы RabbitMQ.
     - **API-шлюз (RED):** карты ошибок и задержек.
     - **MES расчёт:** время расчёта, число таймаутов, загрузка CPU.
     - **Инфраструктура:** утилизация CPU/памяти/диска серверов и БД.
     - **Бизнес-панель:** количество заказов по статусам, среднее время между статусами.
- Настроить алерты с созданием тикета в Jira.
- Внедрить OpenTelemetry SDK во все сервисы (Java, C#) для передачи trace-id в HTTP-заголовках и сообщениях RabbitMQ.
- Развернуть Jaeger для анализа цепочек запросов при поиске «застрявших» заказов.
- Научить команду интерпретировать дашборды и действовать по алертам.
- Еженедельно пересматривать алерты, убирать шумные, добавлять новые по мере эволюции системы.
