# Архитектурное решение по логированию

## 1. Анализ системы и планирование сбора логов

Необходимо собирать логи со всех ключевых компонентов, через которые проходит жизненный цикл заказа:

- **Internet Shop** (Vue) – действия пользователя: создание заказа, загрузка модели.
- **Shop API** (Spring Boot) – приём запросов, сохранение заказа, вызовы MES API, ошибки.
- **CRM** (Vue) – действия продавца: подтверждение заказа.
- **CRM API** (Spring Boot) – обработка запросов CRM, отправка сообщений в RabbitMQ, ошибки.
- **MES** (React) – действия оператора: взятие заказа, смена статуса.
- **MES API** (C#) – расчёт стоимости, управление статусами, взаимодействие с RabbitMQ и БД.
- **RabbitMQ** – логи брокера: публикации, потребления, ошибки доставки.
- **Базы данных (Shop DB, MES DB)** – логи запросов (медленные запросы, ошибки).
- **3D files storage (S3)** – логи доступа к объектам.

**Список событий, логируемых на уровне INFO:**
- Создание заказа (userId, orderId, channel web/api).
- Изменение статуса заказа (orderId, предыдущий статус, новый статус, инициатор – пользователь/оператор/система).
- Отправка сообщения в RabbitMQ (exchange, routingKey, messageId, orderId).
- Получение сообщения из RabbitMQ (queue, messageId, orderId, время обработки).
- Запрос расчёта стоимости (orderId, размер модели в полигонах, результат: успех/ошибка, время выполнения).
- Назначение заказа оператору (orderId, operatorId).
- Ошибки валидации, таймауты, исключения (со стектрейсом на ERROR).
- Авторизационные события (вход, выход, неудачные попытки) – если не противоречит политике безопасности.

**Другие уровни логирования:**
- **DEBUG** – детальные шаги расчёта стоимости, содержимое запросов/ответов (включается только при активном расследовании, чтобы не генерировать избыточный объём).
- **WARN** – повторные попытки отправки сообщений, приближение к лимитам (например, количество соединений БД > 70%).
- **ERROR** – все исключения, сбои интеграций, невозможность сохранить заказ.
- **FATAL** – критические сбои, вызывающие остановку сервиса (например, потеря соединения с БД без возможности восстановления).

## 2. Мотивация

Централизованное структурированное логирование необходимо для:
- **Снижения времени на диагностику (MTTR)** – единый источник логов со всех систем позволяет быстро найти корень проблемы.
- **Проактивного обнаружения инцидентов** – аномалии в логах (всплески ошибок, подозрительная активность) можно заметить до того, как они превратятся в жалобы клиентов.
- **Повышения удовлетворённости клиентов и партнёров** – быстрое решение проблем с заказами восстанавливает доверие.
- **Снижения нагрузки на поддержку** – инженеры первой линии смогут самостоятельно находить ответы, не привлекая разработчиков.
- **Соответствия требованиям безопасности и аудита** – логирование действий с заказами и данными позволяет отслеживать несанкционированный доступ.

**Ключевые метрики, на которые повлияет внедрение логирования:**
1. **MTTR** – среднее время восстановления после сбоя заказа.
2. **Процент заказов, по которым удалось найти причину проблемы без эскалации**.
3. **Количество пропущенных критических ошибок** (отсутствие логов, следовательно клиент сообщает первым).
4. **Время, затрачиваемое на разбор одного инцидента**.
5. **Уровень удовлетворённости клиентов**.


### 2.1 Приоритизация внедрения логирования и трейсинга

Команда не может одновременно внедрить логирование и трейсинг для всех систем. Исходя из критичности для бизнеса и технической сложности, порядок должен быть следующим:

1. **MES API и CRM API** – через них проходят все заказы, они являются источником большинства жалоб. Логи этих сервисов дадут немедленный эффект.
2. **RabbitMQ** – логирование публикаций и потребления позволит отследить потерю сообщений.
3. **Shop API и Internet Shop** – завершит покрытие основного потока B2C.
4. **Базы данных** – логи медленных запросов и ошибок помогут в оптимизации дашборда MES.
5. **Фронтенды (CRM, MES)** – в меньшей степени, т.к. основные ошибки видны на backend.
Трейсинг целесообразно разворачивать параллельно с логированием, но начать с тех же критичных компонентов.


## 3. Предлагаемое решение

Для сбора, хранения и анализа логов предлагается использовать стек **OpenSearch**:
- **OpenSearch** – хранение и индексация логов.
- **OpenSearch Dashboards** – визуализация и поиск.
- **Fluent Bit** – легковесный агент для сбора логов с контейнеров/хостов, парсинг и отправка в OpenSearch. Он менее ресурсоёмок, чем Logstash, что важно для инстансов приложений.
- **OpenSearch Alerting** – встроенный плагин для алертинга по данным логов.

Альтернатива:
- **Yandex Managed Service for Elasticsearch/OpenSearch**, если компания остаётся в Yandex Cloud – это снизит нагрузку на DevOps.

Политика безопасности в отношении логов:
- **Маскирование чувствительных данных:** все поля, содержащие персональные данные (имя клиента, email, адрес), должны маскироваться или шифроваться до записи в лог.
- **Аутентификация и авторизация:** доступ к OpenSearch Dashboards только для сотрудников инженерной команды и поддержки с ролью «Developer»/«Support» через корпоративный LDAP/OAuth.
- **Шифрование:** передача логов от Fluent Bit до OpenSearch по TLS. Хранение данных на дисках OpenSearch с шифрованием.
- **Аудит доступа:** все запросы к логам протоколируются с указанием пользователя.

Политика хранения логов:
- **Индексы:** создаются ежедневные индексы вида `logstash-{service}-YYYY.MM.DD`.
- **Cрок хранения:**
  - Логи уровня INFO – 30 дней.
  - Логи ошибок (ERROR, FATAL) – 90 дней.
  - Логи аудита безопасности – 1 год.

### 4. Превращение системы сбора логов в систему анализа логов

- **Дашборды в OpenSearch Dashboards:**
  - «Сводка по заказам»: распределение статусов, время перехода между статусами, ошибки.
  - «Ошибки API»: топ-5 эндпоинтов по ошибкам.
  - «Интеграция RabbitMQ»: объём очередей.
- **Алертинг:**
  - Резкое увеличение количества ошибок 5xx (более 10 за 5 минут).
  - Появление определённых ключевых фраз в логах (например, «OutOfMemoryError») – немедленное оповещение.
  - Аномалии в частоте событий (например, число создаваемых заказов внезапно выросло в 1000 раз) – срабатывание алерта на возможную DDoS-атаку или сбой.
- **Интеграция с инцидент-менеджментом:** автоматическое создание тикетов при срабатывании критических алертов.

### Обоснование выбора OpenSearch

Для компании оптимальным выбором является **OpenSearch** по следующим причинам:

1. **Лицензия Apache 2.0** – отсутствуют юридические риски, как у Elastic License, и нет затрат на лицензии, как у Splunk. Это важно для растущего бизнеса.
2. **Преемственность с ELK** – команда, знакомая с Elasticsearch/Kibana, легко освоит OpenSearch, а миграция с Managed Elasticsearch в Yandex Cloud возможна с минимальными изменениями.
3. **Наличие встроенного алертинга и обнаружения аномалий** – OpenSearch предоставляет эти функции бесплатно, что позволит реализовать проактивный мониторинг без дополнительных инструментов (в отличие от бесплатной версии ELK, где X-Pack требует платной лицензии).
4. **Масштабируемость и производительность** – проверены в нагрузке, соответствуют ожидаемому росту заказов.
5. **Управляемый сервис в Yandex Cloud** – при использовании Managed Service for OpenSearch/Elasticsearch снижаются затраты на администрирование, что соответствует текущей стратегии компании.

Внедрение OpenSearch как централизованного хранилища логов с Fluent Bit в качестве коллектора обеспечит необходимую функциональность с минимальными затратами и максимальной гибкостью для будущего масштабирования и аналитики.
